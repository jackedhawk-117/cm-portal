# 01 – Project Overview

> **Recruitment prototype – fictional data only. Not affiliated with or endorsed by the Government of Kerala or the Chief Minister’s Office.**
>
> This repository was built for the WhiteMatrix Software Solutions AI Full Stack Engineer
> machine test. Every department, officer, citizen, grievance, reference ID, statistic and
> remark in the seeded database is invented.

## 1. Purpose

The **CM Kerala – Public Grievance Redressal Portal** demonstrates a complete, working
public-service workflow:

1. A citizen files a grievance online.
2. An AI assistant offers a category, department, priority and summary as advice.
3. The Chief Minister’s Office (CMO) reviews the case, checks duplicate flags, and forwards
   it to the right department and officer.
4. The department officer investigates and submits an action-taken report.
5. The CMO accepts the report (resolving the case) or sends it back.
6. The citizen tracks progress, downloads evidence, submits feedback, or reopens the case.

The build favours a **working end-to-end workflow** over visual or optional polish, as
required by the brief.

## 2. Vision and mission

**Vision.** A transparent, citizen-first grievance channel where every submission has a
reference, an owner, a deadline and a visible history.

**Mission.** Prove that a small, well-structured full-stack application can combine
role-based workflow enforcement, human-in-the-loop AI and auditable status tracking without
exposing personal data or letting AI make official decisions.

## 3. Objectives

- Provide an accessible public website that explains the service and lets anyone track a
  grievance by reference ID.
- Give citizens a simple dashboard to submit, follow up, download attachments, rate the
  response and reopen unresolved issues.
- Give the CMO a single operational view: SLA counters, filters, charts, duplicate flags,
  assignment controls, escalation and report review.
- Give department officers a scoped queue that shows only their department’s cases.
- Enforce the workflow on the server with a transition table; every status change is
  written to an immutable history row inside a database transaction.
- Demonstrate responsible AI: advisory suggestions only, explicit acceptance by a human,
  clearly labelled fallback, no personal data in AI audit logs.
- Ship with migrations, deterministic seed data, an automated test suite and deployment
  configuration.

## 4. Users and roles

| Role | Code | What they can do |
| --- | --- | --- |
| Citizen | `CITIZEN` | Register, sign in, submit grievances with optional attachments, analyse text with the AI assistant, track by reference, view own cases, download own complaint evidence, give feedback, reopen resolved cases |
| CMO administrator | `CMO_ADMIN` | View all grievances and statistics, move Submitted/Reopened cases to Under Review, assign a department and officer, override category/department/priority, add internal/public remarks, escalate overdue cases, review action-taken reports, resolve or send back |
| Department officer | `DEPT_OFFICER` | Sign in with seeded credentials, see only cases assigned to their department and in a visible status, view details and attachments, record investigation remarks, submit/resubmit an action-taken report with optional evidence |

The role is stored on the user row and embedded in the signed JWT. The API reloads the user
on every authenticated request, so deactivating an account or changing its department takes
effect immediately.

## 5. Scope

### In scope (implemented)

- Public pages: Home, About Us, How It Works, Departments, Contact Us, FAQ, Track Grievance,
  Login and Register.
- Citizen portal: dashboard counts, filter/search, new grievance form with AI suggestions,
  attachment upload, grievance detail with public timeline, feedback and reopen.
- CMO dashboard: total/pending/resolved/overdue cards, district/category/priority/status
  filters, pagination, search, charts (district, department, status, monthly trend), detail
  actions, duplicate flags, internal and public remarks, escalation.
- Officer dashboard: department queue, priority/status filters, detail view, remarks, action
  report upload, submit for CMO review.
- Server-side workflow transition table with `409 Conflict` for illegal transitions.
- Reference IDs generated by a PostgreSQL sequence in the format `CMK-2026-000123`.
- JWT httpOnly cookie authentication, bcrypt password hashing, role middleware, Zod
  validation, Helmet, CORS allow-list and rate limiting.
- Uploads stored as `bytea` in PostgreSQL (max 5 MB; JPG/PNG/PDF; magic-byte checked) and
  served only through an authorised download endpoint.
- Gemini assistant with structured output, Zod validation and one retry; deterministic
  keyword fallback labelled `source: "fallback-keyword"`; duplicate detection with
  `pg_trgm`; AI audit log without complaint text.
- Public and CMO statistics endpoints, charts fed by real aggregates.
- Jest + Supertest tests covering auth, RBAC, creation, uploads, workflow, tracking and AI
  fallback.
- Migrations, idempotent seed, `render.yaml`, single-service production build and `/api/health`.

### Out of scope / not implemented

- Real government department integration, email/SMS notifications, real identity verification
  (Aadhaar/DigiLocker), file virus scanning, multilingual UI chrome (the AI supports Malayalam
  input; the interface is English), push notifications and native mobile apps.
- Production-grade secret rotation, observability stack, backups and disaster recovery.
- Legal compliance certification (DPDP Act, accessibility audit). The design is
  privacy-conscious but this is a prototype.

## 6. Workflow summary

```
Submitted ──CMO──▶ Under Review ──CMO assign──▶ In Progress
                                                   │
                                     officer report│
                                                   ▼
                                          CMO report review
                                            │           │
                                        ACCEPT      SEND BACK
                                            │           │
                                            ▼           ▼
                                         Resolved   In Progress
                                            │
                              citizen feedback or reopen
                                            │
                                            ▼
                                         Reopened ──CMO──▶ Under Review ──▶ …
```

Only the role listed in the transition table may perform a transition. Assignment is a
separate CMO action that moves `Under Review` or `Reopened` to `In Progress`. Every action
writes a `grievance_history` row, including same-status notes and the assignment event.

| Status | Meaning | Who moves it forward |
| --- | --- | --- |
| `Submitted` | Citizen has filed the case; no owner yet | CMO (to Under Review) |
| `Under Review` | CMO is validating details, AI advice and duplicates | CMO (assign to department) |
| `In Progress` | Department owns the investigation / report | Officer (report), CMO (resolve/send back) |
| `Resolved` | CMO accepted the action-taken report | Citizen (feedback or reopen) |
| `Reopened` | Citizen is not satisfied and gives a reason | CMO (re-review, then assign) |

## 7. Service-level deadlines

Unresolved cases become overdue based on priority:

| Priority | SLA |
| --- | --- |
| High | 3 days |
| Medium | 7 days |
| Low | 15 days |

The values are configurable through `SLA_HIGH_DAYS`, `SLA_MEDIUM_DAYS` and `SLA_LOW_DAYS` and
are returned by `GET /api/meta` and `GET /api/stats/cmo`. The CMO can escalate an overdue
case; escalation raises the priority one level (High stays High) and increments
`escalation_count` with a public history entry.

## 8. Design decisions and assumptions

| Decision | Reason |
| --- | --- |
| Plain JavaScript on the server, JSX on the client | Reduces build complexity and keeps Jest/Supertest reliable under the deadline |
| `pg` with parameterised SQL instead of an ORM | Explicit transactions, easy sequence/`pg_trgm` use, fewer moving parts |
| JWT in an httpOnly, SameSite=Lax cookie | Mitigates XSS token theft and works with same-origin Render deployment; Bearer tokens also accepted for API clients |
| `bytea` attachments in PostgreSQL | Meets the brief and avoids a separate object store; acceptable at prototype scale |
| AI suggestions stored in `ai_*` columns | Official fields are never overwritten automatically; `ai_accepted` records whether the citizen accepted the advice |
| Postgres `pg_trgm` duplicate detection | Deterministic, cheap, explainable and does not require sending personal data to another service |
| Single Render web service | Express serves `client/dist` and `/api` from one origin, simplifying cookies, CORS and deployment |
| Seed data is fictional and deterministic-ish | Dashboards and charts are populated for reviewers; dates are relative to seed time so some cases are overdue |

## 9. Success criteria

- A reviewer can register, submit a grievance with AI advice, receive a reference ID and
  see it in their dashboard.
- The CMO can review, assign to a department/officer, see duplicate flags, and manage SLA.
- The officer sees only their department’s case and can submit an action-taken report.
- The CMO can send the report back and later accept it, resolving the case.
- The citizen can give feedback and reopen; the reopened case returns to CMO review.
- Illegal transitions and cross-role access return `409`/`403`, not silent success.
- The public tracking page shows status and timeline without personal data.
- The test suite passes and the production build serves the SPA and API from one service.
